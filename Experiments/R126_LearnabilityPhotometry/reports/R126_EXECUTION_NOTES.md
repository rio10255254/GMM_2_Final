# Execution notes

The first fixed-example launcher stopped before any optimizer update because its diagnostic trace reader used `trace` instead of the existing model's `traces` field. The model and generated data were not at fault. The initial source is preserved as `scripts/fixed_example_initial.py` and its complete log as `runs/launcher_logs/fixed_example.log`. The retry reads and verifies the same generated bytes, retains the original generator hash and original data check, and writes a separate repeated data check. No expectations or scientific thresholds changed.

The first post-training real trace used the strict-FP32 training/test setup, whereas the frozen real evaluator uses deterministic cuDNN with its library-default TF32 allowance. Algebraic stage reconstruction passed, but comparison to the saved primary image differed by5.02169e-6(normalized intensity), above the pre-fixed3e-6 numerical replay tolerance. The failed source, arrays and result remain in `trace_learned_real.py` and `results/learned_real_trace`.

A separate four-condition runtime experiment (`trace_runtime_diagnosis.json`) held source bytes and weights fixed. Both input normalization routes are bitwise equal. StrictFP32 gives the same5.02169e-6 discrepancy irrespective of deterministic mode; TF32 with non-deterministic selection gives1.26660e-6; the exact primary deterministic/TF32 settings give **zero** difference. The separately retained matched trace explicitly sets those same primary settings and retains the original3e-6 tolerance. No weights, source data, old expected output, primary evaluation, or original failed record was changed. Training and strict tile tests use strictFP32; all8 primary real evaluations share the deterministic/default-TF32 setup. This runtime distinction is now explicit and should be pinned prospectively in future work.
