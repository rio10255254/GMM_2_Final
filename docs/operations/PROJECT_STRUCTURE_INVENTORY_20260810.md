## 主要結構問題

### 1. 論文證據區實際裝了一個 435 GiB 的完整工作系統

`Thesis_MOSR_Evidence/LabSystem_MOSR` 共有 2,138,072 個檔案。它不是單純的論文證據，而是同時包含訓練資料、訓練歷史、實驗、模型封包與重建輸出：

| LabSystem 區域 | 容量 |
|---|---:|
| Training_Data | 331.222 GiB |
| Traing_Progress | 54.269 GiB |
| Experiments | 20.840 GiB |
| Model_Packages | 18.682 GiB |
| Reconstruct_Progress | 9.651 GiB |

其中 R61 與 R62 的資料變體分別佔 114.499 GiB 與 108.307 GiB。多個版本以完整資料集複製表示差異，造成容量、檔案數與路徑長度一起成長。未來必須改成「共同底層資料 + 產生方法 + 差異清單」，不能繼續靠整套複製表示版本。

### 2. 根目錄同時承擔入口、原始採集、分析與歷史

目前根層有 43 個項目。日期型的 100MG、20x、5x、Step 分析與原始資料直接並列，讓第一次接手的人無法從名稱判斷哪個是原始輸入、哪個是正式分析、哪個只是過程輸出。

### 3. 實驗結論與大量過程輸出缺少一致的收尾邊界

在 2026-08-10 清冊中，最大單輪 R63 為 51.481 GiB，幾乎全部位於 `results`；R39、R40、R44、R67、R82、R83 也各自保留大量結果。2026-08-13 的新輪次複核又顯示，真正缺少的是 verdict 後的 closeout 與 D/H 保留邊界，不是每輪都要有完全相同的子資料夾名稱。所有實驗保留 `scripts/reports/results` 核心；當 `results` 超過三個一級項目或 1 GiB，再用該輪的 `results/README.md` 說明正式、精選、活動中與封存候選。

### 4. 同尺寸大型檔案很多，但不能直接當成重複檔

清冊找出 190 組、2,592 個、合計 128.798 GiB 的同尺寸候選。若每組只保留一份，理論上限為 119.928 GiB；但「尺寸相同」不代表「內容相同」，這個數字只能安排後續逐組雜湊核對，不能當成可回收容量。

最大的候選群是 389 個約 69.66 MiB 的模型檔，表面可檢查空間約 26.394 GiB；第二群是 R63 的 402 個約 33.95 MiB checkpoint，表面可檢查空間約 13.292 GiB。

### 5. 版本歷史需要獨立處理

唯讀版本統計顯示：

- 未封裝物件：57.01 GiB。
- 正常封裝：4.07 GiB。
- 一個中斷封裝殘留：19.36 GiB。

這與 `.git` 的 80.454 GiB 總量相符。中斷封裝看起來是高把握候選，但仍要先核對可到達歷史、遠端與工作區狀態，再隔離；不能在活動保護或大量未提交工作存在時直接清除或壓縮。

### 6. 文件存在，但入口不足

專案共有 1,465 份 Markdown，其中只有 53 份位於 `docs`。其餘主要散在論文工作區、舊訓練歷史、各輪實驗與 PSF 工作區。根層只有 8 份可直接閱讀的總覽文件，因此未來需要一份跨區域專案地圖，而不是把所有歷史文件搬進同一個資料夾。

### 7. 既有結構檢查已明確指出實驗治理欠帳

完整結構檢查目前回報 11 個錯誤與 24 個警告。錯誤來自 R61 缺 MANIFEST、R64/R65/R66/R80 Inflection 缺 README 與 MANIFEST、R84/R85 缺 MANIFEST；警告則是 24 個已存在的實驗目錄尚未被 `Experiments/INDEX.md` 引用。這些不是本次清冊新增造成的，但應在未來第 1 階段逐輪確認身分後補齊，不能用空白模板或猜測結論消除警告。
